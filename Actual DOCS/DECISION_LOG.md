Цель: чтобы через месяц (или год) было понятно — *почему* сделано именно так,
а не иначе, и стоит ли это менять.

Формат каждой записи:
- **Статус:** `принято` | `пересматривается` | `отменено`

## ADR-017 · keendwell.com — отдельная splash-страница, отдельный лендинг на dev

- **Дата:** 2026-05-26
- **Статус:** принято

**Контекст:**
Два домена обслуживают разные цели: `keendwell.com` — production-точка входа для клиентов, `dev.keendwell.com` — тестовый/staging-лендинг. До готовности полного лендинга на `keendwell.com` нужно что-то, что не отпугивает посетителей и соответствует бренду.

**Решение:** `keendwell.com` — отдельный HTML-файл (coming soon splash, `/var/www/keendwell/`). `dev.keendwell.com` — полноценный одностраничный лендинг (`/var/www/keendwell-dev/`). В репозитории: `splash/index.html` — splash, корневой `index.html` — лендинг.

**Причина:**
- Splash не перегружает посетителя незаконченным продуктом
- Два независимых файла позволяют выкатывать splash отдельно от лендинга без риска сломать что-то
- Единая OCI-инфраструктура, два nginx vhost — без лишних зависимостей

**Последствия:**
- При переносе полного лендинга на `keendwell.com` — скопировать `index.html` в `/var/www/keendwell/`, убрать splash
- Шрифты и статику splash держать в `splash/fonts/`, не смешивать с корневой папкой
- `Site Versions/ver-3 KEEN·DWELL/` хранит снимок обоих файлов на дату выпуска

## ADR-016 · Трёхцветный вордмарк: KEEN amber · blue DWELL

- **Дата:** 2026-05-26
- **Статус:** принято (визуальная деталь может уточняться)

**Контекст:**
До финала `Wordmark Exploration.html` нужна рабочая цветовая схема вордмарка для сайта и документов. Варианты: монохром (всё amber), двухцвет (amber + white/black), трёхцвет с акцентной точкой.

**Решение:**
- Светлый фон: `KEEN` — `#EABB30` (amber), `·` — `#2E66DB` (синий), `DWELL` — `#0A0A0A` (чёрный)
- Тёмный фон: `KEEN` — `#EABB30`, `·` — `#2E66DB`, `DWELL` — `#ffffff`
- Точка `·` (U+00B7) — самостоятельный акцент в фирменном синем, не amber

**Причина:**
- Синяя точка выполняет роль разделителя и одновременно вводит второй фирменный акцент — референс на технические системы (KNX, BACnet, Home Assistant используют синий)
- Трёхцвет создаёт ритм: тепло → холод → нейтраль, что работает на brand personality (engineering + warmth)
- Amber уже занят логотипом — точка в том же amber сливалась бы с монограммой

**Последствия:**
- CSS-переменная `--blue: #2E66DB` обязательна в `:root` для обоих сайтов
- Классы вордмарка: `.wm-keen`, `.wm-dot`, `.wm-dwell` (или `.lw-keen`, `.lw-dot`, `.lw-dwell` по старым именам)
- При финализации typeface в `Wordmark Exploration.html` — цветовая схема не пересматривается, только шрифт

## ADR-015 · ForoMed как шрифт вордмарка (предварительно)

- **Дата:** 2026-05-26
- **Статус:** принято предварительно (финальный выбор — после `Wordmark Exploration.html`)

**Контекст:**
Для вордмарка `KEEN·DWELL` нужен шрифт с инженерным характером — не утилитарный (Inter), не декоративный (serif). Доступные кандидаты: Inter Bold, ForoMed (TTF, в репо), Pelida Italic Bold (TTF, в репо).

**Решение:** ForoMed (`LOGO/FontsFree-Net-ForoMed-webfont.ttf`) — применён через `@font-face` на обоих сайтах. Загружен в `/fonts/ForoMed.ttf`.

**Причина:**
- ForoMed имеет технически-нейтральный характер без лишней «дизайнерской» нагрузки
- Файл уже в репо и проверен в `brandname.html` ещё до текущей сессии
- Pelida Italic Bold даёт наклон — интересно, но требует проверки читаемости при крупном масштабе на тёмном фоне

**Последствия:**
- Шрифт загружается с сервера (`/fonts/ForoMed.ttf`) — нет зависимости от Google Fonts
- При смене шрифта по итогам Wordmark Exploration — обновить `@font-face`, обновить этот ADR
- Pelida Italic Bold остаётся кандидатом B — файл в репо (`LOGO/Pelida-FontZillion/Fonts/`)

## ADR-014 · Единый социальный хэндл @keendwell

- **Дата:** 2026-05-20
- **Статус:** принято (регистрация хэндлов в процессе)

**Контекст:**
Под бренд KEEN·DWELL нужны социальные сети. Варианты: единый хэндл везде, разные хэндлы под платформу, отказ от соцсетей до накопления контента, отложить решение.

`BRANDING_ROLLOUT_PLAN.md` Phase 0 предлагает более широкий пакет (X, Instagram, LinkedIn, GitHub org, Behance, Dribbble). Пользовательское решение от 2026-05-20 - сузить первую волну до пяти платформ с массовой аудиторией и явным B2B-сигналом, остальные обсуждать отдельно.

**Решение:** единый хэндл `@keendwell` на пяти платформах первой волны:

1. Facebook
2. X (Twitter)
3. Instagram
4. LinkedIn Company
5. YouTube

**Причина:**
- Один хэндл = одна точка узнавания. Можно ставить в футер сайта, email-подпись, визитки, OG/Twitter meta-теги без переключения и пояснений
- Совпадает с доменом `keendwell.com` - визуальная согласованность
- Регистрировать имена надо сейчас, даже без активного контента - иначе их займут (брендовое имя на свободных платформах живёт до первого однофамильца или сквоттера)
- Пять платформ первой волны покрывают основной поведенческий спектр US/UK/EU аудитории: B2C-видимость (Instagram, Facebook), B2B-видимость (LinkedIn), голос/обновления (X), longform/демо (YouTube)

**Последствия:**
- Регистрация хэндлов идёт сейчас (см. CHANGELOG [3.0.0]) - результат фиксировать в этом же ADR обновлением статуса по каждой платформе
- При недоступности `@keendwell` на любой из пяти - решать отдельно (вариативные хэндлы вида `keendwellstudio`, `keendwell_eng` ухудшают brand consistency - предпочтительнее ждать или оспаривать)
- Платформы второй волны (GitHub org, Behance, Dribbble, Threads, Bluesky, Mastodon, TikTok, Pinterest) - отдельным решением; `BRANDING_ROLLOUT_PLAN.md` Phase 0 и `TRADEMARK_RESEARCH.md` §2.2 рекомендуют занять GitHub/Behance/Dribbble заранее даже без активного контента
- Контентная стратегия (что и как часто публикуем) - отдельная задача, не часть этого ADR
- При смене стратегии на локальные хэндлы под регион (`@keendwell.us`, `@keendwell.eu` и т.п.) - вернуться сюда и пересмотреть статус

## ADR-013 · Брендинг KEEN·DWELL + домен keendwell.com

- **Дата:** 2026-05-20
- **Статус:** принято

**Контекст:**
Рабочее имя SmartBuildTech, введённое в ADR-008, оказалось слабым: generic SaaS-вкус, «Smart» и «Tech» - категориальные клише, «Build» прочитывается как general contracting. За несколько раундов нейминга в TLD `.engineering` была отвергнута большая россыпь кандидатов (см. `Fossilized/PROJECT_BRIEF-v1.0.md`, §6: intelli, thread, relay, conduit, lume, casa, atelier, hearth, halo, aurora, nido, anywhere, distance, span, orbit, outpost - занят, bastion - занят, sentinel, bureau, foundry, praxis, lookout, hangar). В финальном раунде по новому словарю победил вариант KEEN·DWELL, и под него удалось взять `.com` напрямую.

Полное обоснование имени (этимология «keen» во всех регистрах, инженерное «dwell time», культурное соседство с журналом Dwell, фонетика, риски) задокументировано в `BRAND_KEENDWELL.md` - этот ADR ссылается на него как на источник правды и не дублирует.

**Решение:**

1. **Имя бренда: `KEEN·DWELL`** (uppercase + middle dot U+00B7, без пробелов вокруг точки).
   - Это и есть каноническое написание бренда во всех user-visible контекстах: копирайт, заголовки, page titles, мета-теги, OG/Twitter card, email subjects и body, alt-текст, ARIA-labels, document headers в репо
   - Источник правды по семантике, voice, tone, позиционированию: `BRAND_KEENDWELL.md` (Brand Bible)
   - Историческое имя SmartBuildTech полностью ретирано - сохраняется только в исторических путях (`Site Versions/ver-2 SmartBuildTech/`, `Fossilized/`)

2. **Форма URL, доменов, email и социальных хэндлов: `keendwell`** (нижний регистр, без разделителя).
   - Применяется только как технический идентификатор
   - В `keendwell.com`, `dev.keendwell.com`, будущих поддоменах (`api.keendwell.com`, `book.keendwell.com`, ...), email-адресах (`studio@keendwell.com`, `hello@keendwell.com`, ...), социальных хэндлах `@keendwell` (см. ADR-014), CSS-классах и code identifiers

3. **Запрещённые формы написания** (не используются ни в копирайте, ни в коде, ни в документах):
   - `KeenDwell`, `Keendwell`, `keenDwell`
   - `Keen Dwell`, `KEEN DWELL` (с пробелом)
   - `Keen-Dwell`, `KEEN-DWELL`
   - `Keen.Dwell`, `keen dwell`
   - `KD` как standalone wordmark (KD-монограмма как favicon / app icon - допустима, но не замена wordmark)
   - `K·D`

4. **Домен и окружения.**
   - TLD: `.com`. Домен `keendwell.com` зарегистрирован
   - Production landing: <https://keendwell.com> - на момент решения отдаёт заглушку «coming soon»
   - Dev / staging: <https://dev.keendwell.com>
   - Защитные домены (`.engineering`, `.io`, `.studio`, `.design`, `.app`) - отдельная задача в `BRANDING_ROLLOUT_PLAN.md` Phase 0, не часть этого ADR

5. **Визуальная форма wordmark (typography only).**
   - Активная разработка в `Wordmark Exploration.html` (корень репо) - typeface, weight, kerning, опциональная KD-монограмма для favicon / app icon / drafting stamp, интеграция с amber-логотипом
   - Exploration касается **только типографической обработки** строки `KEEN·DWELL` и отдельной KD-монограммы. Текст бренда не пересматривается - всегда `KEEN·DWELL`
   - Финальный typographic treatment фиксируется отдельным обновлением Brand Bible §3 и `Actual DOCS/CLAUDE.md` - не требует переоткрытия этого ADR

**Причина:**
- Полное обоснование - в `BRAND_KEENDWELL.md` §§1-4. Кратко: двусоставная семантика «keen» (острый, проницательный, eager) + «dwell» (жилище + dwell time как инженерный термин в 5 дисциплинах) даёт многослойную считываемость - surface-читатель, educated-читатель, инженер и архитектор слышат разные смыслы из одного слова. Соседство с журналом Dwell (premium US architecture) даёт halo без прямой имитации
- Сильная фонетика: спондей /kiːn dwɛl/, sharp opening + warm closing, нет коллизий с consumer-брендами (Orbit, Span, Wrigley)
- `.com` доступен и зарегистрирован - снимает риск домена и даёт universal-recognition во всех целевых регионах. `.engineering` сохраняется как защитный домен в Phase 0, но не canonical
- TM-скан (`TRADEMARK_RESEARCH.md`): композит KEEN·DWELL чист в первом проходе, явных блокеров нет. Внимание к KEEN Home Inc. (class 9, smart vents) - требует attorney clearance перед US class 9 filing
- Uppercase + middle dot как каноническая форма: дёт чёткий визуальный ритм (две равно-весомые половины со средней точкой как структурным разделителем), исключает CamelCase-ассоциации с 2014-era startup-неймингом, читается как осознанная brand-mark, а не как кейсинг-вариация

**Последствия:**

- Все новые упоминания бренда в копирайте/markup - **только `KEEN·DWELL`**. В URL и хэндлах - **только `keendwell`** lowercase
- Любые альтернативные написания запрещены без пересмотра этого ADR (см. список выше). Это правило продублировано в `Actual DOCS/CLAUDE.md` Rule 8
- ADR-008 в части английского языка и янтарного акцента (`#EEB825`) остаётся активным; имя `SmartBuildTech` из ADR-008 заменено настоящим ADR-013 (статус ADR-008 по бренду - заменено ADR-013, по языку/цвету - принято)
- Wordmark в `index.html` (текущая структура `Smart/Build/Tech` в трёх спанах с классами `.lw-smart` / `.lw-build` / `.lw-tech`) подлежит переписыванию на двухчастный wordmark `KEEN·DWELL` с классами `.lw-keen` / `.lw-dot` / `.lw-dwell` - выделено в отдельную задачу (`BRANDING_ROLLOUT_PLAN.md` Phase 2.4), не закрывается этим ADR
- Cal.com slug `time-reserving`, отправитель Resend (`onboarding@resend.dev`, домен `daria.style`), backend-эндпоинт `book.daria.style/api/contact` - миграция на новый бренд решается отдельно в `BRANDING_ROLLOUT_PLAN.md` Phase 0
- Логотип в этой фазе **не меняется** - см. `memory/feedback_use_existing_assets.md` и ADR-009. Возможные импрувы под новый бренд - отдельной задачей
- `README.md` и `Actual DOCS/CLAUDE.md` (v1.3.1) актуализированы под бренд
- `PROJECT_BRIEF.md`, описывавший «working title SmartBuildTech», архивирован в `Fossilized/PROJECT_BRIEF-v1.0.md`. Его §5 (маркетинговая критика прода) и §7 (user-voice-паттерны) сохраняют ценность и используются `BRANDING_ROLLOUT_PLAN.md` как input; §6 (наименование) закрыт Brand Bible

## ADR-012 · Resend + FastAPI для обработки контактной формы

- **Дата:** 2026-05-12
- **Статус:** принято

**Контекст:**
Нужно принимать отправки контактной формы (message, callback, leave contact) и доставлять уведомление владельцу сайта. Варианты: Formspree, EmailJS, Telegram Bot API, собственный бэкенд.

**Решение:** FastAPI + Resend SDK. Бэкенд задеплоен на OCI (порт 8010), проксируется nginx по адресу `https://book.daria.style/api/`. Отправитель: `onboarding@resend.dev` (домен `daria.style` пока не верифицирован в Resend).

**Причина:**
- Полный контроль над структурой и телом письма
- Resend имеет щедрый бесплатный план и надёжный API
- OCI-инстанс уже работает — нет дополнительных инфраструктурных затрат
- FastAPI минимален: один файл `main.py`, один эндпоинт `POST /api/contact`
- CORS ограничен `https://ddl-lsm.github.io` — исключены случайные внешние запросы

**Последствия:**
- Форма не работает при недоступности OCI-инстанса или Resend
- `RESEND_API_KEY` хранится в `.env` на OCI — в репозиторий не попадает
- При верификации домена `daria.style` в Resend — заменить `NOTIFY_FROM` на корпоративный адрес
- Если нужен второй бэкенд-сервис на OCI — занять следующий свободный порт после 8010

## ADR-011 · Cal.com публичный вместо self-hosted

- **Дата:** 2026-05-12
- **Статус:** принято

**Контекст:**
Нужна интеграция бронирования встреч прямо на лендинге (не открывая новую вкладку). Варианты: self-hosted Cal.com на OCI, публичный cal.com, Calendly.

**Решение:** публичный `cal.com/dmitrydm/time-reserving`, встроен через `<iframe>` внутри `.modal-box.wide`. Таймзона браузера передаётся URL-параметром: `?embed=true&timezone=${Intl.DateTimeFormat().resolvedOptions().timeZone}`.

**Причина:**
- Self-hosted Cal.com потребовал Docker + PostgreSQL + nginx-прокси + ручной настройки расписания на отдельном хосте — всё это добавляет сложность без уникального преимущества
- Публичный cal.com работает «из коробки» — расписание и доступность настроены там же
- iframe без embed.js SDK: не нужен JS-инициализатор, нет проблем с React-жизненным циклом
- Явная передача таймзоны устранила баг «No availability» при вызове через лендинг

**Последствия:**
- Зависимость от сервиса cal.com — при смене сервиса достаточно заменить `src` в iframe
- Кастомный домен для календаря (`book.daria.style`) не используется — только `/api/` остался в nginx
- Контейнеры `calcom` и `calcom-db` на OCI остановлены; ресурсы высвобождены

## ADR-010 · Универсальная контактная модалка (ContactModal)

- **Дата:** 2026-05-12
- **Статус:** принято

**Контекст:**
На странице несколько CTA («Tell me more», «I'm interested», «Write to us»). Нужна единая точка сбора контактов с выбором способа связи. Варианты: отдельная страница `/contact`, встроенная форма в секции, modal-попап.

**Решение:** React-компонент `ContactModal` монтируется в корне `App`. Открывается через глобальный мост `window.openContactModal()`. Четыре режима: Schedule a call (Cal.com iframe), Send a message (форма → `POST /api/contact`), Request a callback (форма с выбором платформы), Leave your contact (форма без сообщения).

**Причина:**
- Один компонент обслуживает все CTA — не нужно дублировать логику
- `window.openContactModal` даёт простой интерфейс для кнопок вне React-дерева (если понадобится)
- Modal не покидает страницу — пользователь остаётся в контексте лендинга
- Четыре способа связи покрывают разные предпочтения аудитории

**Последствия:**
- Все новые CTA должны вызывать `window.openContactModal()`, а не ссылаться на `#contact`
- Cal.com iframe загружается только при открытии вкладки «Schedule a call» — лишнего трафика нет
- Стили модалки: `.modal-overlay`, `.modal-box`, `.modal-box.wide` (max-width 820px для iframe), `.cal-iframe` (height 640px)

## ADR-001 · Ванильный HTML/CSS/JS без фреймворков

- **Дата:** 2026-05-10
- **Статус:** принято

**Контекст:**
Лендинг — одна страница. Рассматривались: Next.js, Astro, SvelteKit, просто HTML.

**Решение:** чистый HTML + CSS + JS, без npm, без сборщика.

**Причина:**
- Нет необходимости в роутинге, стейте, SSR
- Деплой = загрузить три файла куда угодно
- Нет зависимостей → нет уязвимостей, нет устаревших пакетов
- Время загрузки минимальное

**Последствия:**
- При масштабировании (блог, кабинет клиента) — потребуется переход на фреймворк
- Нет hot-reload при разработке (решается `npx serve .` или Live Server в VS Code)

## ADR-002 · Тёмная тема как единственная

- **Дата:** 2026-05-10
- **Статус:** принято

**Контекст:**
Обсуждались варианты: только светлая, только тёмная, auto (prefers-color-scheme).

**Решение:** только тёмная тема, без переключателя.

**Причина:**
- Целевая аудитория — технически грамотные люди (разработчики, предприниматели в IT)
- Тёмная тема ассоциируется с профессионализмом в dev-сфере
- Градиенты и акцентный цвет выглядят значительно лучше на тёмном фоне
- Одна тема = вдвое меньше CSS для поддержки

**Последствия:**
- Если маркетинг решит расширить аудиторию — понадобится светлая тема или переключатель
- Все новые компоненты проектируются только под тёмный фон

## ADR-003 · Акцентный цвет — фиолетовый (#c77dff / #7b61ff)

- **Дата:** 2026-05-10
- **Статус:** отменено (заменено ADR-008)

**Контекст:**
Рассматривались синий (доверие), зелёный (технологии), фиолетовый (инновации + премиум).

**Решение:** фиолетовый градиент `#c77dff → #7b61ff`.

- Хорошо сочетается с тёмным фоном, создаёт ощущение "глубины"
- Ассоциации: инновации, технологии, премиум-сегмент

- Не хардкодить цвет нигде за пределами `:root`

## ADR-006 · CSS без методологий (не BEM, не CSS Modules)

- **Дата:** 2026-05-10
- **Статус:** принято

**Контекст:**
Варианты: BEM, Tailwind, CSS Modules, просто классы.

**Решение:** плоские классы с семантическими именами (`.card`, `.hero-title`, `.btn-primary`).

**Причина:**
- Проект — один файл, одна страница. BEM избыточен.
- Tailwind требует сборщика (противоречит ADR-001)
- Специфичность намеренно плоская — без `!important`, без вложенных селекторов глубже 2 уровней

**Последствия:**
- При росте CSS > 1000 строк стоит разделить на файлы или перейти на методологию
- Не добавлять `!important` — если нужно перебить стиль, проверь специфичность

## ADR-007 · GitHub Actions для автодеплоя

- **Дата:** 2026-05-10
- **Статус:** принято

**Контекст:**
Нужен автодеплой статики. Варианты: Vercel, Netlify, GitHub Pages вручную, GitHub Actions + Pages.

**Решение:** GitHub Actions workflow (`deploy.yml`) → GitHub Pages.

- При добавлении сборки (минификация, оптимизация) — расширять тот же `deploy.yml`, не создавать новый

## ADR-008 · English как основной язык страницы + янтарный акцент

- **Дата:** 2026-05-10
- **Статус:** принято (по языку и цвету); часть про имя SmartBuildTech заменена ADR-013

**Контекст:**
v1.x — русскоязычная страница с фиолетовым акцентом под российскую аудиторию.
При ребрендинге в SmartBuildTech целевая аудитория смещена: US/UK/EU (smart home, custom app dev, AI integration).
Фиолетовый никак не связан с логотипом и не ассоциируется с «умным домом».

**Решение:** английский язык, акцентный цвет `#EEB825` (R:236 G:175 B:33) — точно совпадает с жёлтыми элементами логотипа.

**Причина:**
- Англоязычный рынок — основной источник заказов
- Жёлтый/янтарный: энергия, тепло, технологии умного дома — семантически точнее фиолетового
- Цвет взят из логотипа → визуальная согласованность без подбора «на глаз»
- Контраст жёлтого (#EEB825) на тёмном (#0c0c0e) — WCAG AA по luminance ratio

**Последствия:**
- Все новые CSS-цвета — через переменные `--accent: #EEB825`, `--accent-2: #F5C842`, `--accent-glow: rgba(238,184,37,0.14)`
- При локализации на другие языки — добавлять `lang`-атрибут и отдельный HTML-файл, не менять `index.html`
- Имя бренда SmartBuildTech, введённое в этом ADR, заменено на KEEN·DWELL в ADR-013. Английский и жёлтый акцент - остаются

## ADR-009 · Логотип: использовать существующие PNG, обрабатывать Python для тёмного фона

- **Дата:** 2026-05-10
- **Статус:** принято

**Контекст:**
Оригинальный логотип (`LOGO/logo27-5.1-square-1-600x600.png`) — белый фон, жёлтые и тёмные элементы.
Нужна версия для тёмного фона `#0c0c0e`.
Рассматривались: CSS `filter: invert()`, SVG-реконструкция вручную, Python/Pillow попиксельная обработка.

**Решение:** Python + Pillow, BFS flood-fill для отделения фона от внутренних бликов.

Алгоритм:
1. BFS от краёв изображения — идентифицировать «фоновые» белые пиксели (связные с границей)
2. Фоновые пиксели → `rgba(0,0,0,0)` (прозрачность)
3. Тёмные пиксели (lum < 90, sat < 0.30) → `rgb(255,255,255)` (белые на тёмном фоне)
4. Жёлтые пиксели (r>150, g>90, b<130, r>g>b) → `rgb(236,175,33)` — точный цвет акцента
5. Внутренние блики (белые, не связанные с краями) → остаются белыми `rgb(255,255,255)`

**Причина:**
- `filter: invert()` даёт грязный тёмно-коричневый вместо жёлтого
- SVG-реконструкция «из головы» — ошибка: логотип создан автором и должен использоваться as-is
- BFS точно разграничивает «фон» и «блики внутри элементов» без numpy (только stdlib PIL)

**Последствия:**
- Скрипт генерации: одноразовый, не входит в production-сборку
- `LOGO/logo-dark.png` — коммитится как артефакт, не пересоздаётся автоматически
- При обновлении исходного логотипа — запустить скрипт повторно вручную
